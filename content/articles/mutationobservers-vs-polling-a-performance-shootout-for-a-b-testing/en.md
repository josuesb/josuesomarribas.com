<p dir="auto">Every client-side experiment starts with the same problem: the element you want to change doesn't exist yet when your code runs. Two strategies dominate the solutions. You can poll, asking the DOM every hundred milliseconds whether the element has arrived, or you can observe, registering a callback that the browser fires when the DOM actually changes. Both work. The interesting question is what each one costs, and the answer is less one-sided than the conventional wisdom suggests.</p><p dir="auto">I've defended polling before. In <a href="/blog/javascript-i-write-every-week-in-an-a-b-testing-role">the JavaScript I write every week in an A/B testing role</a>, the waitForElement helper uses setInterval, and I stand by it for the cases it was written for: it's simple, predictable, and hard to break. This post is the longer answer, with numbers, about where that simplicity stops being free.</p><h2 dir="auto">The benchmark, read fairly</h2><p dir="auto">The most quotable comparison comes from Alex MacArthur, who measured attaching a listener to a late-mounted element with both strategies: <a href="https://macarthur.me/posts/use-mutation-observer-to-handle-nodes-that-dont-exist-yet/">polling with a zero-delay setTimeout came out around 88 times slower than a MutationObserver</a>, on top of the observer's simpler cleanup story.</p><p dir="auto">Read that number fairly, though. Nobody polls at zero delay in production; a realistic 100ms interval costs a few dozen querySelector calls before the element shows up, which is negligible CPU on any modern device. The honest framing is that polling's cost is not throughput but latency and granularity:</p><ul dir="auto"><li data-preset-tag="p"><p><strong>Latency.</strong> With a 100ms interval, your change lands on average 50ms after the element appears, and in the worst case a full interval later. That window is exactly where visible flicker lives, because the user can see the original element before your variant replaces it.</p></li><li data-preset-tag="p"><p><strong>One-shot blindness.</strong> The typical polling helper stops after the first match. If the framework re-renders and replaces your modified node two seconds later, the test silently reverts and nobody is notified.</p></li></ul><p dir="auto">A MutationObserver fires in the same event-loop turn as the change, per <a href="https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver">the MDN specification of the API</a>, and it keeps firing for as long as you keep it connected. Those two properties are the whole case for it.</p><h2 dir="auto">Where observers earn their keep</h2><p dir="auto">Single-page applications are the decisive environment. Frameworks create and destroy DOM constantly, and an Accenture front-end team working on exactly this problem documented the core trap: <a href="https://medium.com/frontend-at-accenture/a-b-testing-dynamic-content-using-mutation-observers-3ad3bff2031a">if the element you observe is destroyed by the SPA, mutations stop firing even when it's recreated, so the observer must watch the app's stable main container instead</a>. Combine a container-level observer with idempotent apply functions and your variant survives re-renders indefinitely, the pattern I detailed in <a href="/blog/idempotency-for-mortals-javascript-snippets-rerenders">idempotency for mortals</a>.</p><p dir="auto">The canonical shape, including the disconnect-mutate-reconnect step that prevents your own changes from re-triggering the callback:</p><pre data-language="JavaScript"><code>const container = document.querySelector('#app') || document.body;

const observer = new MutationObserver(() =&gt; {
  observer.disconnect();
  applyVariant(); // idempotent: checks its own marker before acting
  observer.observe(container, { childList: true, subtree: true });
});

applyVariant();
observer.observe(container, { childList: true, subtree: true });</code></pre><h2 dir="auto">Where observers cost you</h2><p dir="auto">The API's reputation for danger comes from real incidents, and they share a profile: a subtree observer on a huge, busy page with an expensive callback. Mixmax, whose product lives inside Gmail's DOM, <a href="https://engineering.mixmax.com/blog/precisely-observing-structural-page-changes">found their global subtree MutationObservers to be a significant performance problem and re-architected away from them</a>. Gmail mutates constantly; if your callback runs querySelector over a large tree on every batch, you've built a busy-loop with extra steps.</p><p dir="auto">The mitigations are mechanical, and I covered them in depth in <a href="/blog/mutationobservers-without-panic-performance-guide">MutationObservers without panic</a>: observe the narrowest stable container, keep the callback to a cheap existence check, disconnect as soon as your work is done, and always pair the observer with a timeout so a selector that never matches doesn't leave machinery running for the whole session.</p><h2 dir="auto">The decision table I actually use</h2><ul dir="auto"><li data-preset-tag="p"><p><strong>Static page, element present at or shortly after load, change below the fold:</strong> polling. The latency doesn't matter, the code is three lines, and a junior teammate can debug it at a glance.</p></li><li data-preset-tag="p"><p><strong>SPA, or any page where the target re-renders:</strong> observer on a stable container plus idempotent apply. Polling here produces the silent-revert bug, which is worse than slow because it corrupts the test without failing it.</p></li><li data-preset-tag="p"><p><strong>Above-the-fold change where flicker is the risk:</strong> observer, because the latency budget is effectively zero. The flicker problem deserves its own discussion of validity, which is the subject of the cost of FOUC.</p></li><li data-preset-tag="p"><p><strong>Hostile or unknown page (third-party widgets, heavy mutation):</strong> observer with strict scoping and a timeout, or reconsider whether the change belongs client-side at all.</p></li></ul><h2 dir="auto">The implication</h2><p dir="auto">The shootout framing undersells the real lesson: these are tools for different failure modes. Polling fails loud and cheap (the change just doesn't apply); observers fail quiet and expensive (the page slows down for everyone). Pick based on which failure your test can afford, and write the choice into your QA checklist, the same one I walk through in <a href="/blog/how-i-qa-an-a-b-test-before-it-goes-live">how I QA an A/B test before it goes live</a>, so the next person inherits a reason instead of a habit.</p><p dir="auto"><em>Related reads: </em><a href="/blog/mutationobservers-without-panic-performance-guide"><em>MutationObservers without panic</em></a><em>, </em><a href="/blog/idempotency-for-mortals-javascript-snippets-rerenders"><em>idempotency for mortals</em></a><em>, and </em><a href="/blog/javascript-i-write-every-week-in-an-a-b-testing-role"><em>the JavaScript I write every week</em></a><em>.</em></p>
